# 本機能力診斷 — 里程碑切片

**日期**: 2026-08-29
**權威來源**: [`.planning/ROADMAP.md`](../../.planning/ROADMAP.md) 的「下一里程碑：可靠性與可診斷性」。本文件不重新定義該里程碑的目標或非範圍，只展開其中一個切片的實作規格；兩者衝突時以 ROADMAP 為準。

## 切了哪幾條

里程碑的範圍共十條。本切片取其中六條——診斷核心與分層、五個具名設定檔、啟動前自動檢查與阻斷／警告行為、無副作用探測與雙格式輸出、適配器與備份的前置條件、祕密不落地。

留給後續切片的四條自成一組，全部圍繞 **來源追溯清單** 與續作：線上服務最終失敗時的修復資訊與進度保留、**作品工作流程狀態清單** 的保存、**階段依賴關係** 的失效傳播與 **階段發佈** 的原子性、**舊版產物** 的處置與指定階段重新產生。這四條依賴同一套 manifest 機制，拆開做只會做兩次。

時長的兩個實作誰是權威，是本切片實作時會撞到但 ROADMAP 未明文的問題，已獨立記錄為 ADR-0002，不在本文件內。

## Problem Statement

使用者現在無法在執行前知道一個工作流程能不能跑完。

本機前置檢查分散在各功能裡，沒有單一入口。Go 輔助工具的位置被寫死成「本專案隔壁一定有 kinetitext-go 這個 repo」——在 Carl 的機器上是真的，所以問題看不出來；在重新 clone 的環境、CI、或專案搬過位置之後，需要 Go 的階段會在跑到一半以晦澀的子程序錯誤失敗，而不是在開始前就說清楚「這台機器沒有 Go 輔助工具，MP4 轉檔會改走 ffmpeg，會比較慢」。這違背 CONTEXT.md 對 **Go 輔助工具** 的定義：它是選用的增強能力，不健康時核心流程仍應以既有替代能力維持可用。

同樣的問題也出現在其他前置條件上。需要瀏覽器的三個網站適配器、備份需要的 rclone 與具名遠端設定、TTS 需要的設定，現在都只能在實際請求時才知道行不行。

## Solution

執行任何流程之前，先評估對應的 **工作流程設定檔**，回報這個流程能不能進行，以及每一項能力是可用、以替代能力降級、還是阻斷。

阻斷項不可略過，流程不會啟動；警告則說明將採取的回退行為並自動繼續。同一份判定同時供 CLI、TUI 與工作流程啟動點使用，輸出有人類可讀與 JSON 兩種格式，CLI 在選取範圍內存在阻斷項時以非零結束碼結束。

## User Stories

1. 作為第一次 clone 這個 repo 的開發者，我想要在跑 yt-pipeline 之前看到「Go 輔助工具不可用」的明確訊息，這樣我就不用從子程序的錯誤堆疊反推是路徑問題。
2. 作為在 CI 上跑測試的維護者，我想要 Go 輔助工具缺席時流程仍能以 ffmpeg 完成，這樣 CI 不必為了通過而安裝一個選用元件。
3. 作為把專案搬到別的目錄的使用者，我想要二進位位置能用環境變數指定，這樣我不需要維持特定的 repo 相鄰擺法。
4. 作為在多台機器間切換的使用者，我想要明確的命令列參數優先於環境變數與預設路徑，這樣單次執行的覆寫不會污染我的長期設定。
5. 作為要跑 MP4 轉檔的使用者，我想要在流程開始前知道這次會走 Go 還是 ffmpeg，這樣我能預估要等多久。
6. 作為評估降級是否可接受的使用者，我想要警告說明具體的回退行為（較慢、而非結果不同）並自動繼續，這樣我不必為了一個可接受的降級而重下一次指令。
7. 作為遇到阻斷項的使用者，我想要流程直接不啟動而不是提供略過選項，這樣我不會半途才失敗並留下半成品。
8. 作為想單獨做健康檢查的使用者，我想要一個手動診斷指令，這樣我能在不啟動任何流程的情況下看到整台機器的狀態。
9. 作為跑手動診斷的使用者，我想要預設檢查全部設定檔、也能只選其中一個，這樣我既能總覽也能聚焦。
10. 作為把診斷接進腳本的使用者，我想要 JSON 輸出，這樣我不必解析人類可讀的文字。
11. 作為在 CI 裡跑診斷的維護者，我想要選取範圍存在阻斷項時得到非零結束碼，這樣 CI 能直接失敗而不需要判讀輸出。
12. 作為看人類可讀輸出的使用者，我想要阻斷與警告在視覺上明確區分，這樣我一眼知道哪些是真的擋住我。
13. 作為遇到阻斷的使用者，我想要訊息附帶可行的修復資訊，這樣我知道下一步該裝什麼或設什麼。
14. 作為爬取純 HTTP 站點的使用者，我想要瀏覽器能力不要成為我的阻斷項，這樣我不會因為缺 Chromium 而無法爬一個根本不需要瀏覽器的站。
15. 作為爬取需要瀏覽器的站點的使用者，我想要 **網站適配器前置條件** 在網址解析到該適配器之後才被檢查並回報，這樣我得到的是針對這個站的診斷。
16. 作為適配器的維護者，我想要每個適配器能宣告自己的本機能力需求，這樣新增一個需要瀏覽器的站不必修改評估邏輯本身。
17. 作為使用備份流程的使用者，我想要評估只確認 rclone 存在與 **備份遠端設定** 可辨識，不要提前去連遠端，這樣診斷不會因為網路狀況而變慢或誤報。
18. 作為執行診斷的使用者，我想要看到三支 Go 輔助工具各自的狀態而不是一個總體的「Go 可用」，這樣某一支二進位缺失時我知道是哪一支。
19. 作為關心可重現性的使用者，我想要診斷輸出包含實際解析到的工具版本，這樣我能對照後續切片記錄的 **來源追溯清單**。
20. 作為處理祕密設定的使用者，我想要輸出只出現 **祕密設定指紋** 而不是設定值本身，這樣我可以安全地把診斷貼給別人看。
21. 作為在慢速或異常環境下執行的使用者，我想要每次探測都有逾時，這樣一個沒有回應的外部工具不會讓診斷永遠卡住。
22. 作為改變主意的使用者，我想要能取消進行中的診斷，這樣我不必等它跑完。
23. 作為關心副作用的使用者，我想要探測不寫入任何檔案、不修改任何設定，這樣我可以隨時安心執行它。
24. 作為跑 TUI 的使用者，我想要選單顯示最近一次診斷摘要並允許重新檢查，這樣我不用切出去用 CLI。
25. 作為從 TUI 啟動流程的使用者，我想要即使剛看過摘要，真正啟動前仍會即時驗證一次，這樣我不會用到已經過期的判定。
26. 作為同時用 CLI 與 TUI 的使用者，我想要兩邊對同一個設定檔給出一致的結果與修復資訊，這樣我不會因為入口不同而得到矛盾的答案。
27. 作為關心效能的使用者，我想要探測只確認可執行與版本可取得、不做效能測試，這樣啟動成本可以忽略。
28. 作為重複執行流程的使用者，我想要同一次執行內的探測結果被沿用而不是每個階段重探一次，這樣不會累積不必要的子程序啟動。
29. 作為撰寫新流程的開發者，我想要新增一個工作流程設定檔就能取得可進行判定，這樣我不必自己拼裝檢查邏輯。
30. 作為審閱這次改動的人，我想要評估邏輯是純函式、探測是它的輸入，這樣測試不需要真的裝上 Go 輔助工具。

## Implementation Decisions

**診斷核心拆成兩層**：能力探測負責與外界互動（解析二進位並取版本、確認 ffmpeg 存在、確認 rclone 與具名遠端設定存在、確認瀏覽器可用），評估本身是接受探測結果並輸出判定的純函式。這是本切片唯一的架構決策，也是讓「Go 不在時如何降級」能在沒裝 Go 的機器上完整測到的原因。

**判定為三態**（可用／以替代能力降級／阻斷）而非布林值，因為降級與阻斷對使用者的意義完全不同：前者說明回退行為後自動繼續，後者不可略過且流程不啟動。

**五個具名設定檔**：`crawl`、`audiobook`、`m4b`、`youtube`、`backup`。手動診斷預設檢查全部，亦可指定其一。設定檔本身不執行流程，符合 CONTEXT.md 對此詞的界定。

**Go 二進位解析改為優先序鏈**，取代目前唯一的固定相對路徑：明確傳入的路徑參數優先，其次環境變數，其次既有的相鄰 repo 路徑（保留為本機開發預設），皆無則判定為不可用。三支輔助工具各自解析、各自回報狀態，不共用一個總體旗標。

**降級是每個階段的屬性**，不是全域開關。具備 ffmpeg 替代路徑的階段在 Go 不可用時降級；沒有替代路徑的能力使該流程阻斷。這讓 CONTEXT.md 要求的「Go 不健康時核心流程仍可用」由結構保證，而不是靠呼叫端各自記得處理。

**網站適配器前置條件延後檢查**：能力需求由適配器自身宣告，並且只在網址解析到該適配器之後才進入爬取設定檔的檢查項。需要瀏覽器的三個適配器因此不會讓純 HTTP 的爬取被阻斷。這同時為瀏覽器相依的延遲載入建立了正當性，但延遲載入的實作不在本切片內。

**備份只做本機檢查**：確認 rclone 可執行、且具名遠端設定存在且可辨識。不預先驗證遠端連線或權限——那是里程碑的明文非範圍。

**探測無副作用、具逾時與取消能力**，且同一次執行內結果沿用，不在每個階段重新解析二進位與取版本。

**兩種輸出格式共用同一份判定結構**：人類可讀格式明確區分阻斷與警告並附修復資訊；JSON 格式結構穩定可供腳本消費。CLI 在選取範圍內存在阻斷項時以非零結束碼結束。

**祕密只以祕密設定指紋出現**於判定結構與兩種輸出，遵循 ADR-0001。

## Testing Decisions

好的測試在這裡指的是：只透過模組對外承諾的行為斷言，不斷言它內部怎麼探測、怎麼拼路徑。評估層是純函式，這讓絕大多數情境——Go 缺席、只缺其中一支、瀏覽器缺席、rclone 缺席、祕密遮蔽、三態判定、五個設定檔的差異——都能以構造出來的探測結果覆蓋，完全不需要真的裝上那些工具。

**沿用既有 seam，不開新的**。評估在既有的 Go 二進位路徑解析測試上延伸，涵蓋優先序鏈（參數 > 環境變數 > 開發預設 > 不可用）與三態判定；輸入是構造的探測結果，輸出是判定，不碰檔案系統。兩種輸出格式在同一個 seam 上驗證：同一份判定分別渲染，斷言 JSON 結構穩定、人類可讀格式區分阻斷與警告、兩者都不含祕密值。適配器前置條件的延後檢查在既有的適配器測試檔驗證：純 HTTP 站點的網址不會讓瀏覽器能力成為阻斷項，需要瀏覽器的站點的網址則會。

非零結束碼與探測逾時需要真的跑起來，放在既有的整合測試層，沿用既有「Go 不在就跳過」的模式，不新增測試基礎設施。

瀏覽器相依的延遲載入**不寫測試**——它唯一的可觀察行為只能靠子程序檢查模組圖來驗證，那會是一個新 seam 且價值可疑。

## 驗收條件

對應 ROADMAP 完成條件，本切片負責前三條與第四條的一半：

- CLI 與 TUI 從同一診斷核心取得一致的設定檔結果與修復資訊。
- 診斷區分阻斷與警告；CLI 可輸出 JSON，且本次選取範圍存在阻斷項時以非零結束碼結束。
- TUI 顯示最近診斷摘要並允許重新檢查，且真正啟動流程前仍會即時驗證。
- 自動化測試覆蓋設定檔判定、阻斷／警告與祕密遮蔽；可用環境另執行真實工具整合測試。（同條件中的失效傳播、舊版產物、原子發佈及續作屬後續切片。）
