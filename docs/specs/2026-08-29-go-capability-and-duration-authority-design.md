# Go 輔助工具可用性與時長權威來源

**日期**: 2026-08-29
**狀態**: ready-for-agent（尚未發佈至 issue tracker，見文末）

## Problem Statement

使用者現在無法在執行前知道一個工作流程能不能跑完。

Go 輔助工具的位置被寫死成「本專案隔壁一定有 kinetitext-go 這個 repo」。在 Carl 自己的機器上這是真的，所以問題看不出來；但在任何重新 clone 的環境、CI、或把專案搬過位置之後，需要 Go 的階段會在跑到一半時以晦澀的子程序錯誤失敗，而不是在開始前就說清楚「這台機器沒有 Go 輔助工具，MP4 轉檔會改走 ffmpeg 路徑，會比較慢」。這直接違背 CONTEXT.md 對 **Go 輔助工具** 的定義——它是選用的增強能力，不健康時核心流程仍應以既有替代能力維持可用。

同時，音訊時長現在有兩個彼此獨立的來源：music-metadata 與 Go 的 duration 輔助工具，兩條路徑都活著，呼叫端拿到的是一個裸數字，看不出它從哪來。ADR-0001 要求 **來源追溯指紋** 納入適用的外部工具版本，用來判定 **階段產物** 是否仍可重用。當同一個階段可能由兩個不同實作產生時長、而 **來源追溯清單** 又分不出是哪一個時，續作判定就不可靠：使用者可能重用一個實際上由另一條路徑、以不同精度算出的產物，或反過來被迫重跑一個其實有效的階段。

## Solution

執行前先給出一份判定，執行時只有一個權威答案。

使用者啟動任何一個流程（爬取、TTS、合併、M4B、MP4、yt-pipeline）之前，系統評估對應的 **工作流程設定檔**，回報這個流程能不能進行，以及每一項能力是可用、以替代能力降級、還是阻斷。Go 輔助工具不在時，具備 ffmpeg 替代路徑的階段自動降級並在報告中標明降級原因與預期影響；真正無法進行的流程在開始前就被擋下並說明缺什麼。

時長改為單一權威來源：Go 的 duration 輔助工具可用時由它決定，不可用時降級到 music-metadata。無論走哪一條，回傳值都帶著來源標記與工具版本，讓 **來源追溯清單** 能忠實記錄這個 **階段產物** 是由哪一條路徑產生的，兩種來源產生的產物不會被誤判為等價。

## User Stories

1. 作為第一次 clone 這個 repo 的開發者，我想要在跑 yt-pipeline 之前看到「Go 輔助工具不可用」的明確訊息，這樣我就不用從子程序的錯誤堆疊反推是路徑問題。
2. 作為在 CI 上跑測試的維護者，我想要 Go 輔助工具缺席時流程仍能以 ffmpeg 完成，這樣 CI 不必為了通過而安裝一個選用元件。
3. 作為把專案搬到別的目錄的使用者，我想要二進位位置能用環境變數指定，這樣我不需要維持特定的 repo 相鄰擺法。
4. 作為在多台機器間切換的使用者，我想要明確的命令列參數優先於環境變數與預設路徑，這樣單次執行的覆寫不會污染我的長期設定。
5. 作為要跑 MP4 轉檔的使用者，我想要在流程開始前知道這次會走 Go 還是 ffmpeg，這樣我能預估要等多久。
6. 作為評估降級是否可接受的使用者，我想要報告說明降級的具體影響（較慢、而非結果不同），這樣我能決定是要等還是先去裝 Go 輔助工具。
7. 作為爬取純 HTTP 站點的使用者，我想要瀏覽器能力不要成為我的阻斷項，這樣我不會因為缺 Chromium 而無法爬一個根本不需要瀏覽器的站。
8. 作為爬取需要瀏覽器的站點的使用者，我想要 **網站適配器前置條件** 在網址解析到該適配器之後才被檢查並回報，這樣我得到的是針對這個站的診斷。
9. 作為適配器的維護者，我想要每個適配器能宣告自己的本機能力需求，這樣新增一個需要瀏覽器的站不必修改評估邏輯本身。
10. 作為執行診斷的使用者，我想要看到每一項 Go 輔助工具各自的狀態而不是一個總體的「Go 可用」，這樣某一支二進位缺失時我知道是哪一支。
11. 作為關心可重現性的使用者，我想要診斷輸出包含實際解析到的工具版本，這樣我能對照 **來源追溯清單** 裡記的版本。
12. 作為處理祕密設定的使用者，我想要診斷輸出只出現 **祕密設定指紋** 而不是設定值本身，這樣我可以安全地把診斷貼給別人看。
13. 作為使用備份流程的使用者，我想要評估只確認 **備份遠端設定** 存在且可辨識，不要提前去連遠端，這樣診斷不會因為網路狀況而變慢或誤報。
14. 作為跑 TUI 的使用者，我想要選單在我選定一個動作時就顯示該流程的可進行判定，這樣我不用先跑一次才知道會失敗。
15. 作為建立 M4B 的使用者，我想要每一章的時長來自單一權威來源，這樣章節標記不會因為兩套實作的細微差異而累積偏移。
16. 作為合併音訊的使用者，我想要合併前後的時長由同一條路徑量測，這樣容差比對比的是真正的差異而不是實作差異。
17. 作為續作一個中斷工作的使用者，我想要系統辨認出上次的時長是由降級路徑產生的，這樣它不會把它當成權威路徑的產物直接重用。
18. 作為裝上 Go 輔助工具之後回頭續作的使用者，我想要既有的降級時長產物被判定為需要重新產生，這樣我的最終輸出建立在一致的來源上。
19. 作為檢視 **作品工作流程狀態清單** 的使用者，我想要看到每個時長產物的來源與版本，這樣我能理解續作判定為什麼是那樣。
20. 作為擁有 **舊版產物** 的使用者，我想要缺少來源標記的既有時長不被自動重用，這樣我不會拿到來源不明的結果。
21. 作為呼叫時長服務的開發者，我想要回傳值就帶著來源與版本而不是裸數字，這樣我不可能忘記把它記進來源追溯。
22. 作為 yt-pipeline 的使用者，我想要既有的合併容差設定繼續有效且語意不變，這樣這次改動不會改變我已經習慣的行為。
23. 作為在兩條路徑之間比對的維護者，我想要有明確定義的時長容差來判斷兩者是否相容，這樣「不一致」是一個可檢查的條件而不是主觀判斷。
24. 作為排查時長異常的使用者，我想要日誌記下這次用了哪條路徑，這樣我能把異常對應到實作。
25. 作為關心效能的使用者，我想要能力探測只確認可執行與版本可取得，不要做效能測試，這樣啟動成本可以忽略。
26. 作為重複執行流程的使用者，我想要同一次執行內的探測結果被沿用而不是每個階段重探一次，這樣不會累積不必要的子程序啟動。
27. 作為撰寫新流程的開發者，我想要新增一個工作流程設定檔就能取得可進行判定，這樣我不必自己拼裝檢查邏輯。
28. 作為審閱這次改動的人，我想要評估邏輯是純函式、探測是它的輸入，這樣測試不需要真的裝上 Go 輔助工具。

## Implementation Decisions

**工作流程設定檔評估拆成兩層**：能力探測負責與外界互動（解析二進位、取版本、確認 ffmpeg 存在、確認備份遠端設定存在），評估本身是接受探測結果並輸出判定的純函式。判定對每一項能力回報「可用 / 以替代能力降級 / 阻斷」三態，而非布林值，因為降級與阻斷對使用者的意義完全不同。評估不執行流程，符合 CONTEXT.md 對此詞的界定。

**Go 二進位解析改為優先序鏈**，取代目前唯一的固定相對路徑：明確傳入的路徑參數優先，其次環境變數，其次既有的相鄰 repo 路徑（保留為本機開發預設），皆無則判定為不可用。三支輔助工具（音訊轉換、時長、MP4 轉檔）各自解析、各自回報狀態，不共用一個總體旗標。

**降級是每個階段的屬性**，不是全域開關。具備 ffmpeg 替代路徑的階段在 Go 不可用時降級並在報告中標明；沒有替代路徑的能力使該流程阻斷。這確保 CONTEXT.md 所要求的「Go 不健康時核心流程仍可用」是由結構保證的，而不是靠呼叫端各自記得處理。

**網站適配器前置條件延後檢查**：能力需求由適配器自身宣告，並且只在網址解析到該適配器之後才進入爬取設定檔的檢查項。需要瀏覽器的三個適配器因此不會讓純 HTTP 的爬取被阻斷。這同時為瀏覽器相依的延遲載入建立了正當性，但延遲載入的實作不在本 spec 內。

**時長權威來源選定為 Go 的時長輔助工具**，music-metadata 為降級路徑。理由是 Go 版本是 ADR-0001 明確要求記錄版本的外部工具，且效能正是 Go 層存在的理由。這個選擇要另立一則 ADR，因為它難以逆轉（既有產物的有效性判定跟著它走）且是真實取捨。

**時長服務的公開介面改為回傳結構化結果**——時長值、來源路徑標記、該路徑的工具版本——而非裸數字。這是本 spec 唯一的破壞性介面變更，M4B 建構、MP4 轉檔與 yt-pipeline 三處下游需跟進。理由是把來源資訊做成型別上無法忽略的東西，比依賴呼叫端自律更可靠。

**來源追溯記錄實際使用的路徑與版本**。由降級路徑產生的階段產物與由權威路徑產生的不視為等價：**來源追溯指紋** 納入路徑標記，因此裝上 Go 輔助工具後回頭續作時，先前的降級產物會被正確判定為需要重新產生。缺少來源標記的既有時長屬 **舊版產物**，保留但不自動重用。

**兩條路徑的一致性以明確容差定義**。yt-pipeline 既有的容差旗標語意不變、行為不變；本 spec 只是讓被比較的兩個數字帶有來源，並在兩者來源不同時於日誌標明。

**探測結果在單次執行內沿用**，不在每個階段重新解析二進位與取版本。

**祕密只以祕密設定指紋出現**於評估輸出與來源追溯，診斷輸出不得揭露設定值，遵循 ADR-0001。

## Testing Decisions

好的測試在這裡指的是：只透過模組對外承諾的行為斷言，不斷言它內部怎麼探測、怎麼拼路徑。評估層是純函式，這讓「Go 不可用時流程如何降級」可以完全不裝 Go 輔助工具就測到——這正是把探測與評估分層的主要理由。

**沿用既有 seam，不開新的**。工作流程設定檔的評估在既有的 Go 二進位路徑解析測試上延伸，涵蓋優先序鏈（參數 > 環境變數 > 開發預設 > 不可用）與三態判定；輸入是構造出來的探測結果，輸出是判定，不碰檔案系統。時長掛在時長服務的公開 API 這個既有 seam 上，既有的時長服務單元測試與 Go 時長整合測試是現成的 prior art：前者以構造的探測結果驗證權威／降級的選擇與結構化回傳，後者在 Go 輔助工具實際存在時驗證真實版本字串能進到結果裡。既有的整合測試已經有「Go 不在就跳過」的模式，沿用它，不新增測試基礎設施。

下游三處（M4B、MP4、yt-pipeline）的既有測試需要跟著介面變更調整，但不為它們新增 seam——它們驗證的仍是既有的外部行為（章節標記位置、容差比對結果），只是時長的取得方式換了。

適配器前置條件的延後檢查在既有的適配器測試檔驗證：斷言純 HTTP 站點的網址不會讓瀏覽器能力成為阻斷項，需要瀏覽器的站點的網址則會。

瀏覽器相依的延遲載入**不寫測試**。它唯一的可觀察行為是「爬純 HTTP 站點時不載入 Chromium 相關模組」，只能靠子程序檢查模組圖來驗證，那會是一個新 seam 且價值可疑。

## Out of Scope

依賴清理的實作全部不在本 spec 內，包含移除未宣告且實際無作用的編碼轉換相依、以內建亂數識別取代 uuid 套件、WebSocket 客戶端改用執行期內建實作、檔案 I/O 統一到 Bun 內建、HTTP 客戶端改用原生 fetch，以及瀏覽器相依的延遲載入。這些是零決策或純一致性的改動，直接做比寫規格快。

架構文件技術棧表的修正（它列了兩個實際上沒在用的套件）同樣不在本 spec 內，但已知需要處理。

ADR-0001 的 **作品工作流程狀態清單** 與 **階段發佈** 主體實作不在本 spec 內。本 spec 只確保時長與 Go 工具版本能以正確的形狀餵進 **來源追溯指紋**，不負責清單本身的讀寫與原子性。

## Further Notes

需要新增一則 ADR 記錄時長權威來源的選擇，並依 decision-records 的要求附上 `**Falsified if:**` 段落——該段落以反引號標示的檔案即構成這個決策的邊界清單，供工具讀取，因此標記本身是承載語意的，不是裝飾。

本 spec 的兩個部分共用同一個根因：CONTEXT.md 已經為「Go 輔助工具是選用的」寫好了語言，但實作假設它必然存在。時長的雙來源是同一個假設在另一處的表現。兩者一起做才會讓詞彙表與程式碼對齊。
